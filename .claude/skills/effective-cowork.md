# スキル: 効果的な Claude Code / Cowork 運用ガイド

## 概要
Claude Code の使用量を最小化しながら、成果を最大化するためのベストプラクティス集。
このスキルは、タスク依頼の仕方・分割・事前準備に関するナレッジを体系化したものです。

---

## 原則1: CLAUDE.md を常に最新に保つ（トークン節約効果: 最大）

### なぜ重要か
- CLAUDE.md がないと、毎セッションでコードベース探索に数万トークンを浪費する
- プロジェクト構造・規約・コマンドを事前に伝えることで、探索ステップを大幅に削減

### やるべきこと
- プロジェクトのルートに CLAUDE.md を配置する
- 技術スタック、ディレクトリ構造、開発コマンド、コーディング規約を記載する
- 新機能追加・構造変更のたびに CLAUDE.md を更新する
- ドメイン用語の定義を含める（特にビジネスロジックが複雑な場合）

---

## 原則2: タスクを適切な粒度に分割する

### アンチパターン（高コスト）
```
❌ 「採用管理ダッシュボードを作って」（→ 4,000行以上を一括生成、エラー時の手戻りが甚大）
❌ 「セキュリティも追加して」（→ 全ファイルを再読する必要がある）
```

### ベストプラクティス（低コスト・高品質）
```
✅ ステップ1: 「型定義（types/index.ts）とストア（lib/store.ts）を作って」
✅ ステップ2: 「候補者のCRUD APIを作って」
✅ ステップ3: 「候補者一覧ページを作って。バリデーションも含めて」
✅ ステップ4: 「テストを書いて実行して」
```

### 目安
- **1タスク = 1〜5ファイルの変更** が最適
- 1タスクが10ファイル以上に及ぶ場合は分割を検討
- 各タスクに「完了条件」を明記する（テスト通過、ビルド成功など）

---

## 原則3: 仕様を最初から明確にする（後追い修正を防ぐ）

### アンチパターン
```
❌ まず機能を作る → あとでセキュリティ追加 → あとでバリデーション追加
   （3回分のコスト: 実装 + 再読 + 修正 × 2回）
```

### ベストプラクティス
```
✅ 「候補者APIを作って。要件:
   - CRUD操作
   - 入力バリデーション（名前500文字、メモ5000文字制限）
   - JSON解析エラーハンドリング
   - ペイロードサイズ制限100KB」
   （1回のコストで完了）
```

---

## 原則4: テストファーストで自律ループを回す

### なぜ重要か
- テストがあれば Claude が自分でエラーを検知・修正できる
- テストがないと「作成 → ユーザーが確認 → 修正依頼」の往復が発生（2倍のコスト）

### やるべきこと
- 新機能の依頼時に「テストも書いて、実行して通ることを確認して」と含める
- テストフレームワーク（Vitest, Jest等）をプロジェクトに事前導入しておく

---

## 原則5: Cowork（並列エージェント）を効果的に使う

### 並列化に適したタスク
- 独立したページ/コンポーネントの同時作成
- テストの作成と実装の同時進行
- リファクタリングとドキュメント更新の同時進行

### 並列化に適さないタスク（直列にすべき）
- 型定義 → その型を使うコード（依存関係あり）
- API → そのAPIを呼ぶフロントエンド（依存関係あり）

### Cowork の使い方
```
✅ 「エージェント1: 候補者API、エージェント2: 求人API」（独立 → 並列OK）
❌ 「エージェント1: 型定義、エージェント2: その型を使うAPI」（依存 → 直列にすべき）
```

---

## 原則6: コンテキストを引き継ぐ

### セッション間のコンテキスト維持
- CLAUDE.md に「現在の作業状態」セクションを追加し、進行中のタスクを記録
- `git status` + `git log --oneline -5` で現状をすぐ把握できるようにする

### 1セッション内のコンテキスト維持
- 長いセッションでは定期的に「ここまでの変更を要約して」とまとめさせる
- 大量のファイルを読ませるより、関連ファイルだけをピンポイントで指定する

---

## 原則7: プロンプトの書き方を最適化する

### 高コストなプロンプト
```
❌ 「このコードを改善して」（曖昧 → 探索コスト大）
❌ 「バグがある」（情報不足 → 全ファイル調査が必要）
```

### 低コストなプロンプト
```
✅ 「src/app/api/candidates/route.ts の POST ハンドラに、
   メールアドレスの重複チェックを追加して」
✅ 「src/lib/store.ts:42行目付近の addCandidate で、
   タグが空配列の場合にエラーになる。デフォルト値を設定して」
```

### ポイント
- **ファイルパスを具体的に指定する**（探索トークンを節約）
- **行番号や関数名を含める**（ピンポイントで読める）
- **期待する動作を明記する**（試行錯誤を減らす）
