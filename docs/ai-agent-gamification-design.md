## 1. エグゼクティブサマリー

「何かを作りたい」という明確な目的を持たない一般ユーザーが、**ゲームを遊ぶ感覚でAIエージェントを制作・育成・共有できる**Webプラットフォームを構築する。

本設計の核心となる判断は次の3点である。

1. **エージェントを「コード」ではなく「データ（宣言的スペック）」として定義する。**
   ユーザーが作るものはプログラムではなく、性格・スキル（ツール）・知識・行動ルールを組み合わせた「キャラクターシート」である。これにより、ターミナルもGitHubも一切露出させずに済み、同時にサンドボックス化・モデレーション・リミックス（他人の作品の継承）が構造的に容易になる。

2. **ゲームの経済システムを実コスト制御と一体化させる。**
   LLMのトークン消費を「エナジー」、ツールのアンロックを「スキルツリー」として表現する。ゲームデザインがそのままレートリミット・コスト管理・安全性のゲーティングとして機能する。

3. **「作る楽しさ」より先に「動く喜び」を届ける。**
   初回セッション5分以内に、自分のエージェントが目の前で動き、何かを成し遂げる体験（First Agent Moment）を保証する。制作の深さは後から段階的に開放する。

MVPは約3〜4ヶ月（エンジニア3〜4名想定）で到達可能と見積もる。詳細は[ロードマップ](#10-開発ロードマップ)参照。

## 2. プロダクトビジョンとコンセプト

### 2.1 ビジョン

> 「開発」を、観る・遊ぶ・競うエンターテインメントに変える。

OpenCanvasやHermes Agentのようなエージェント構築の潮流は、今後「一般の人がエージェントを持つ・育てる」方向に大衆化する。そのとき最大の障壁は技術力ではなく、**「作りたいものがない」「作り方の概念モデルがない」**ことである。ゲームはこの2つを同時に解決する装置になり得る。クエストが「作る理由」を与え、キャラクター育成のメタファーが「作り方の概念モデル」を与える。

### 2.2 ターゲットユーザー

| ペルソナ | 特徴 | 求める体験 |
|---|---|---|
| **プレイヤー層**（主ターゲット） | プログラミング未経験。スマホゲーム・SNS利用者 | 遊びながら「自分のAI」ができる驚き、シェアして反応をもらう喜び |
| **クリエイター層** | ノーコードツール経験者、ChatGPTヘビーユーザー | より深いカスタマイズ、作品が評価・利用されること |
| **観戦者層** | 作らないが観る・使う人 | 他人のエージェントを試す、イベントを観戦する |

観戦者層を明示的に設計対象に含める点が重要。**「作る人1 : 使う人9」の構造を前提**とし、使う・観る側の体験がクリエイターへの報酬（評価・利用数）を生む循環を作る。

### 2.3 体験の一言コンセプト

**「たまごっち × ポケモン × Minecraft を、AIエージェントで。」**

- **たまごっち**: 自分のエージェントが「いる」感覚。日々成長し、話しかけられる。
- **ポケモン**: 収集・育成・対戦（エージェント同士のタスク対決）・交換（リミックス）。
- **Minecraft**: 素材（スキル・知識・性格パーツ）の組み合わせによる自由なクラフト。

## 3. ゲームデザイン（コアループと進行設計）

### 3.1 コアループ

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ①クエスト受注 ──▶ ②クラフト ──▶ ③テスト実行 ──▶ ④公開/シェア
   （作る理由の提供）  （パーツ組立）   （動く喜び）      │
                                                       ▼
   ⑦次の目標 ◀── ⑥報酬・アンロック ◀── ⑤評価・利用される
   （新クエスト/イベント） （新スキル/素材）  （いいね/利用数/対戦結果）
```

- **1周目のループを5分以内**に完了させる（チュートリアルクエスト）。
- ループの各段に必ず「即時フィードバック」を置く（実行ログの演出、通知、リアクション）。

### 3.2 エージェント = キャラクター のメタファー対応表

| ゲーム概念 | 実体（技術的実装） |
|---|---|
| キャラクター | エージェント（宣言的スペック一式） |
| 性格・ボイス | システムプロンプトのペルソナ部（テンプレート＋パラメータ） |
| スキル / わざ | ツール（Web検索、画像生成、計算、外部API等）の装備スロット |
| 知識 / アイテム | ナレッジ（ユーザーがアップロードしたドキュメント → RAG） |
| レベル / 経験値 | 利用実績・評価に応じた進行度。上位スキルのアンロック条件 |
| 装備スロット数 | 同時装備できるツール数（レベルで拡張） |
| エナジー | LLMトークン予算（時間回復 or 課金） |
| バトル / 競技 | 同一タスクを複数エージェントに与え、結果を審査員（LLM+人間投票）が採点 |
| 交配 / 継承 | 他ユーザーのエージェントのリミックス（fork）。系譜が記録される |

### 3.3 進行設計（プログレッション）

**プレイヤーレベル**と**エージェントレベル**を分離する。

- **プレイヤーレベル**: クエスト達成・制作数・評価で上昇。**新しいツール種別・クラフト機能のアンロック条件**を兼ねる。
  → これは安全性ゲーティングでもある。外部にアクセスできる強力なツール（Webhook送信等）は高レベル＋実績のあるユーザーにのみ開放する（詳細は[§8](#8-安全性モデレーションコスト制御)）。
- **エージェントレベル**: そのエージェントが使われた回数・評価で上昇。ステータス表示や見た目の進化など、**愛着を生む演出**に使う。

**スキルツリー例（プレイヤー）**:

```
Lv1: 会話ペルソナ編集、プリセットツール（検索・計算）
Lv3: ナレッジ装備（ファイルアップロード → RAG）
Lv5: マルチステップ行動ルール（「〜のときは〜する」カード）
Lv8: 画像生成ツール、定時実行（スケジュール）
Lv12: 外部連携ツール（審査制）、エージェント連携（パーティ編成）
```

### 3.4 同期性・イベント性（要件3-aへの回答）

| イベント種別 | 内容 | 同期性の実装 |
|---|---|---|
| **ウィークリークエスト** | 毎週のお題（例:「旅行プランを提案するエージェントを作れ」） | 締切と結果発表の共有体験 |
| **エージェントバトル（大会）** | 同一タスクを参加エージェントが一斉実行、トーナメント形式で審査 | 実行のライブ観戦（ストリーミング表示）、リアルタイム投票 |
| **ライブ共同クラフト** | 配信者やコミュニティで1体を投票しながら共同制作 | WebSocketによる共同編集・投票 |
| **シーズン** | 3ヶ月単位でテーマ・報酬・ランキングをリセット | シーズンパス的な進行 |

**エージェントの実行過程そのものを「観戦コンテンツ」にする**のが本プロダクト固有の面白さである。思考ログ・ツール呼び出しを、RPGの戦闘ログのように演出してリアルタイム配信する（例:「🔍 スキル発動: Web検索!」「💭 考え中…」）。技術的にはLLMストリーミング＋WebSocketファンアウトで実現する（[§7.4](#74-実行の可視化観戦)）。

### 3.5 ソーシャル・評価設計

- **ギャラリー**: 公開エージェントの一覧。カテゴリ・タグ・トレンド。
- **試遊**: 他人のエージェントをワンタップで試せる（エナジーは試遊者側が消費 → クリエイターに経験値還元）。
- **リミックス**: 公開エージェントをforkして改造。**系譜（親子関係）を必ず表示**し、元作者にも経験値が入る。パクリ問題を「継承は名誉」という文化設計で反転させる。
- **評価**: いいね・利用数・リミックス数・バトル戦績の複合スコア。

## 4. プロダクト設計上の最重要決定事項

スタッフエンジニアとして、初期に固定すべきアーキテクチャ決定（ADR相当）を挙げる。

### ADR-1: エージェントは「宣言的スペック」であり、ユーザーコードは実行しない

**決定**: ユーザーが作成するのは JSON で表現される `AgentSpec`（ペルソナ、ツール装備、ナレッジ参照、行動ルール）のみ。任意コードのアップロード・実行は**スコープ外**とする（将来、審査制プラグインとして検討）。

**理由**:
- 一般ユーザーにコードは不要（要件2-a）。UIはカード/スロットの組み合わせで完結する。
- サンドボックスの攻撃対象面が劇的に減る。実行するのは「我々が書いたランタイム」だけであり、ユーザー入力はデータとしてしか流れない。
- リミックス・差分表示・モデレーション（静的検査）が構造的に可能になる。
- ツールは運営が実装・審査した「公式アイテム」のみ。品質と安全性を運営が保証できる。

**トレードオフ**: 表現力の上限が下がる。→ 上級者向けには「行動ルールカード」（イベント条件×アクションのビジュアルルール）で段階的に表現力を足す。それでも足りない層は本プロダクトのターゲット外と割り切る。

### ADR-2: 実行はすべてサーバーサイド。クライアントはビューに徹する

**決定**: LLM呼び出し・ツール実行はすべてバックエンドのAgent Runtimeで行う。APIキーや生プロンプトはクライアントに出さない。

**理由**: コスト制御（エナジー消化の正確な計測）、プロンプト盗用防止、モデレーション挿入点の確保、観戦（1実行をN人に配信）の実現。

### ADR-3: ゲーム経済とコスト管理を同一システムにする

**決定**: エナジー残高・消費・回復を管理する Economy サービスを単一の真実の源とし、LLM呼び出しは必ずエナジー引き落としと同一トランザクション（論理的に）で行う。

**理由**: フリーミアムでLLMを使わせるサービスの最大の事業リスクはトークンコストの暴走。ゲームUIとしての「エナジー」が、そのままハードリミットとして機能する設計にすれば、コスト上限が構造的に保証される。

### ADR-4: モノリス（モジュラーモノリス）で開始する

**決定**: MVPは単一のバックエンドアプリケーション＋独立したAgent Runtimeワーカーの2サービス構成。マイクロサービス分割はしない。

**理由**: チーム規模（3〜4名）とイテレーション速度優先。ただしモジュール境界（`game` / `agents` / `social` / `economy` / `runtime`）はコード上で明確に切り、将来の分離に備える。Agent Runtimeだけは負荷特性（長時間実行・スパイク）が異なるため最初からワーカーとして分離する。

## 5. システムアーキテクチャ

### 5.1 全体構成図

```
                          ┌─────────────────────────────┐
                          │        クライアント           │
                          │  Next.js (Web / PWA)         │
                          │  ・クラフトUI（カード/スロット）│
                          │  ・実行観戦ビュー（ログ演出）   │
                          │  ・ギャラリー/イベント         │
                          └──────┬─────────────┬────────┘
                                 │ HTTPS (tRPC/REST)│ WebSocket
                                 ▼                  ▼
      ┌──────────────────────────────────────────────────────┐
      │                  API Gateway / BFF                    │
      │              （認証・レート制御・入力検証）              │
      └───┬──────────┬──────────┬──────────┬─────────────────┘
          ▼          ▼          ▼          ▼
      ┌────────┐ ┌────────┐ ┌────────┐ ┌─────────┐
      │ Game   │ │ Agent  │ │ Social │ │ Economy │   ← モジュラーモノリス
      │ (quest,│ │ (spec, │ │(gallery│ │(energy, │      （単一デプロイ）
      │ event, │ │ craft, │ │ like,  │ │ ledger) │
      │ season)│ │ remix) │ │ battle)│ │         │
      └────┬───┘ └───┬────┘ └───┬────┘ └────┬────┘
           │         │          │           │
           ▼         ▼          ▼           ▼
      ┌──────────────────────────────────────────┐
      │   PostgreSQL（主データ） + Redis（キャッシュ/ │
      │   セッション/リアルタイムPub-Sub）           │
      └──────────────────────────────────────────┘
                       ▲
                       │ ジョブキュー（実行リクエスト）
                       ▼
      ┌──────────────────────────────────────────┐
      │            Agent Runtime（ワーカー群）      │
      │  ・AgentSpec → 実行計画のコンパイル          │
      │  ・LLM呼び出し（Claude API）＋ストリーミング  │
      │  ・ツール実行（サンドボックス内・許可リスト制） │
      │  ・実行イベントを Redis Pub/Sub へ発行       │
      └──────┬───────────────┬───────────────────┘
             ▼               ▼
      ┌────────────┐  ┌──────────────────┐
      │ LLM API     │  │ ツール実行環境      │
      │ (Claude等)  │  │ (検索API, 画像生成, │
      │             │  │  RAG/Vector DB 等) │
      └────────────┘  └──────────────────┘
```

### 5.2 主要コンポーネントの責務

| コンポーネント | 責務 |
|---|---|
| **BFF/API** | 認証（OAuth: Google/Apple/LINE）、入力検証、レートリミット、tRPC/RESTエンドポイント |
| **Game モジュール** | クエスト定義・達成判定、イベント（大会）進行、シーズン、レベル・アンロック管理 |
| **Agent モジュール** | AgentSpecのCRUD・バージョニング・リミックス系譜、クラフトUIのマスタデータ（ツールカタログ、ペルソナテンプレート） |
| **Social モジュール** | ギャラリー、いいね・利用数集計、バトルのマッチング・審査集計、通知 |
| **Economy モジュール** | エナジー台帳（残高・消費・回復・購入）、全LLM消費の記帳。**追記型台帳（ledger）で実装**し、残高はイベントの集計とする |
| **Agent Runtime** | 実行リクエストをキューから取得 → スペックをコンパイル → エージェントループ実行 → イベントストリーム発行。ステートレスな水平スケール対象 |
| **Realtime配信** | Redis Pub/Sub → WebSocketゲートウェイ。実行ログ観戦・イベントのライブ投票・共同編集 |

### 5.3 リアルタイム系の設計

- 実行1件 = 1チャンネル（`run:{run_id}`）。観戦者はチャンネル購読するだけで同じストリームを見られる（追加のLLMコストゼロで観戦者数をスケールできる — 観戦コンテンツ化の技術的な裏付け）。
- MVPでは Redis Pub/Sub + 自前WSゲートウェイで十分。同時接続が万を超える段階で Ably/Pusher 等のマネージド移行を検討。
- ライブイベント（大会）は同一チャンネル設計の上に投票メッセージを重ねるだけで成立する。

## 6. データモデル

主要エンティティ（簡略版）:

```
users(id, handle, level, xp, created_at, ...)

agents(id, owner_id, name, status[draft/published/suspended],
       parent_agent_id,          -- リミックス系譜
       current_version_id, level, xp, ...)

agent_versions(id, agent_id, spec_json, created_at)
  -- spec_json = AgentSpec（下記）。イミュータブル。公開=特定バージョンの固定

tools(id, key, name, tier, unlock_level, schema_json, safety_class)
  -- 運営管理の「公式アイテム」カタログ

knowledge_docs(id, owner_id, agent_id, storage_ref, index_status)
  -- アップロード文書。Vector DBへの索引と対応

runs(id, agent_version_id, requester_id, trigger[chat/quest/battle/schedule],
     status, energy_cost, started_at, finished_at)
run_events(run_id, seq, type[thought/tool_call/tool_result/message], payload, ts)
  -- 観戦・リプレイ・監査のすべてに使う。追記のみ

energy_ledger(id, user_id, delta, reason[run/recharge/purchase/reward], ref_id, ts)

quests(id, season_id, type, spec_json, starts_at, ends_at)
quest_progress(user_id, quest_id, state, ...)

battles(id, quest_id, status, ...)
battle_entries(battle_id, agent_version_id, run_id, judge_score, vote_count)

likes(user_id, agent_id), follows(...), notifications(...)
```

### AgentSpec（ユーザーが「作る」ものの実体）

```jsonc
{
  "version": "1.0",
  "persona": {
    "template": "friendly_guide",      // 運営提供テンプレート
    "params": { "tone": "casual", "emoji": true },
    "custom_instructions": "旅行好きのお姉さん。関西弁。"  // 自由記述（モデレーション対象）
  },
  "skills": [                          // 装備ツール（スロット数はレベル依存）
    { "tool": "web_search", "config": {} },
    { "tool": "image_gen", "config": { "style": "watercolor" } }
  ],
  "knowledge": [ { "doc_id": "kd_123" } ],   // RAG参照
  "rules": [                           // 行動ルールカード（Lv5〜）
    { "when": "user_asks_price", "then": "always_cite_source" }
  ],
  "appearance": { "avatar_id": "av_777", "color": "#7B5CFF" }
}
```

ポイント:
- **バージョンはイミュータブル**。公開・バトル参加・リミックスはすべて特定バージョンを指す。再現性と監査性を担保。
- 自由記述は `custom_instructions` に閉じ込め、モデレーションパイプラインの検査対象を限定する。

## 7. エージェント実行基盤（Agent Runtime）

### 7.1 実行フロー

```
実行リクエスト（chat/quest/battle/schedule）
  → Economy: エナジー事前引当（予約）
  → キュー投入 → Runtimeワーカーが取得
  → AgentSpec をシステムプロンプト＋ツール定義にコンパイル
  → エージェントループ:
       LLM呼び出し（ストリーミング）
       → ツール呼び出し要求があれば許可リスト検証 → 実行 → 結果を戻す
       → 完了 or ステップ上限まで反復
  → run_events へ逐次記録 & Pub/Sub発行
  → Economy: 実消費で精算（予約との差分返却）
```

### 7.2 スペックのコンパイル

`AgentSpec` → プロンプトへの変換は**運営管理のテンプレートエンジン**で行う。ユーザー入力（custom_instructions等）は明示的にデリミタで区切り、「ユーザー定義部はツール権限を変更できない」構造にする（プロンプトインジェクション対策の第一層）。

### 7.3 ツール実行

- ツールはすべて運営実装。ネットワークアクセスはツール実装内の許可ドメインのみ。
- ツールごとに `safety_class`（safe / rate_limited / reviewed）を持ち、実行時にユーザーレベル・エージェント状態と突合。
- 将来のサードパーティツール開放時は、マニフェスト審査＋実行分離（gVisor/Firecracker等のマイクロVM）を前提とする。**MVPでは不要**（ADR-1により任意コード実行がないため、通常のコンテナ分離で足りる）。

### 7.4 実行の可視化（観戦）

`run_events` の各イベントに演出メタデータ（アイコン、エフェクト種別）をランタイムで付与し、クライアントは「戦闘ログ風」にレンダリングする。**思考の生ログは要約層を通してから配信**する（プロンプト盗用と不適切内容の露出防止。LLMの思考をHaiku級の軽量モデルで一行実況に変換する、など）。

### 7.5 バトル（競技）の審査

1. 同一タスク・同一入力を各エントリーエージェントに実行させる（並列、同一ステップ上限）。
2. **LLM審査員**（ルーブリック採点、複数回実行の平均）＋**観客投票**の合成スコア。
3. 採点プロセス自体も `run_events` として公開し、納得感を担保する。

## 8. 安全性・モデレーション・コスト制御

一般ユーザー×UGC×LLMという構成上、ここが事業の生命線。多層防御で設計する。

### 8.1 コンテンツ安全（多層）

| 層 | 内容 | タイミング |
|---|---|---|
| 1. 静的検査 | `custom_instructions`・ナレッジ文書の公開時モデレーション（LLM分類器＋NGワード） | 公開申請時 |
| 2. 実行時ガード | システムプロンプトでの役割固定、出力のセーフティフィルタ | 毎実行 |
| 3. 事後対応 | 通報機能、`runs`/`run_events` の完全監査ログ、エージェントの `suspended` 状態 | 常時 |
| 4. 段階的信頼 | 強力なツール・公開機能はレベル＆実績でゲート（ゲーム進行と一体化） | 構造的 |

### 8.2 コスト制御（エナジー経済）

- **ハードリミット**: エナジー残高なしでは実行不可。事前引当→実消費精算のため、超過は最大でも1実行分。
- **モデルの使い分け**: 通常会話は中位モデル、バトル審査や高度なクエストのみ上位モデル。実況・要約はHaiku級。→ エナジー消費レートに差をつけ、ゲーム的な「コスト感覚」として自然に見せる。
- **無料枠の設計**: 時間回復エナジー（例: 5分で1回復、上限50）。ソーシャルゲームのスタミナ設計をそのまま原価管理に転用。
- **キャッシュ**: ペルソナテンプレート・ツール定義部はプロンプトキャッシュで原価を下げる。

### 8.3 個人情報・権利

- ナレッジアップロードは公開エージェントに紐付ける際に再確認フロー（個人情報を含む文書の公開事故防止）。
- リミックスは規約で明示ライセンス化（公開＝リミックス許諾。系譜表示で還元）。

## 9. 技術スタック提案

| レイヤ | 技術 | 選定理由 |
|---|---|---|
| フロントエンド | **Next.js (App Router) + TypeScript + Tailwind** | PWA化でモバイル体験を先行確保。ゲームUIはまずDOM/CSSアニメ＋Lottieで十分（Canvas/WebGLは演出強化フェーズで） |
| クラフトUI | カード＆スロットUI（自作コンポーネント）。ルールカードが複雑化したら **React Flow** | ノードエディタから入らない。一般ユーザーには「装備画面」メタファーの方が通じる |
| API | **tRPC**（社内BFF）+ 最小限のREST | フロント/バック一体開発の速度優先 |
| リアルタイム | WebSocket（自前GW + Redis Pub/Sub）→ 規模拡大時にマネージド | §5.3 |
| バックエンド | **TypeScript (Node.js/Fastify) モジュラーモノリス** | フロントと言語統一、採用容易性、LLM SDKの充実 |
| ジョブキュー | **BullMQ (Redis)** → 規模拡大時にSQS等 | MVPの運用コスト最小化 |
| DB | **PostgreSQL**（+ pgvector でRAG開始） | Vector DB専用品は索引規模が伸びてから |
| LLM | **Claude API**（会話・審査・実況で

モデル階層を使い分け） | ペルソナ追従・ツール使用の品質、プロンプトキャッシュによる原価削減 |
| インフラ | コンテナ（ECS/Fargate or Cloud Run）+ CDN | Runtimeワーカーだけ独立スケーリング |
| 監視 | OpenTelemetry + Sentry + LLM専用の消費ダッシュボード | エナジー台帳と実トークン消費の突合を日次で |

## 10. 開発ロードマップ

前提: エンジニア3〜4名（フルスタック2、バックエンド/インフラ1、＋ゲームUI/デザイン1）。

### Phase 0: 体験プロトタイプ（〜6週）
**ゴール: 「5分でFirst Agent Moment」が成立するかの検証**
- クラフトUI（ペルソナ＋ツール2種）→ 即実行 → 戦闘ログ風の実行演出、まで一本道
- 認証・エナジーは仮実装。社内＋クローズドユーザーテスト（N=20）
- **判断点**: 非エンジニアが説明なしで1体作れるか。演出は「面白い」か

### Phase 1: MVP（+10〜12週）
**ゴール: クローズドβ公開**
- コアループ完成: チュートリアルクエスト、ギャラリー公開、試遊、いいね
- エナジー経済（時間回復のみ、課金なし）、モデレーション層1〜3
- ナレッジ装備（RAG）、プレイヤーレベルとアンロック
- 観戦チャンネル（公開実行の閲覧）

### Phase 2: ソーシャル＆イベント（+8週）
**ゴール: オープンβ。リテンションの柱を立てる**
- リミックス（系譜）、ウィークリークエスト、初回のエージェントバトル大会
- 通知、フォロー、ランキング
- 課金（エナジーパック / シーズンパス検証）

### Phase 3: エコシステム（以降）
- シーズン制、ライブ共同クラフト、スケジュール実行（エージェントの自律活動）
- 審査制の外部連携ツール、クリエイター還元プログラム
- モバイルネイティブ化の判断

各フェーズ末に**継続率とコスト原単位（DAUあたりLLM原価）**でGo/No-Go判断を行う。

## 12. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| LLM原価がフリーミアムで逆ザヤ | 事業継続性 | エナジー=ハードリミット（ADR-3）、モデル階層化、キャッシュ、P1で原単位計測 |
| 「作っても面白くない」（エージェントの出力が期待外れ） | コア体験の毀損 | ペルソナテンプレートの品質に先行投資。「自由に作らせる」より「良い型を選ばせる」を優先 |
| 不適切UGC（ペルソナ・ナレッジ経由） | 信頼・法務 | §8.1の4層防御。公開は審査後、通報SLA設定 |
| プロンプトインジェクション（ナレッジ文書経由等） | 権限逸脱 | ツール許可リストはスペック外で強制（プロンプトでは変更不能）、外部到達ツールのレベルゲート |
| バトル審査の納得感が得られない | イベントの失速 | LLM審査＋観客投票のハイブリッド、採点根拠の公開 |
| 同期イベントの過疎（初期ユーザー数不足） | イベント体験の空洞化 | P2までは非同期イベント（締切共有型）中心。同時接続前提の企画はDAUが閾値を超えてから |
| スコープ肥大（エディタの高機能化要求） | 出荷遅延 | ADR-1を防衛線に。「コードが書きたい人」は明示的にターゲット外 |

## 13. 未決事項（Open Questions）

1. **収益モデルの主軸**: エナジー課金 / シーズンパス / クリエイターサブスクのどれを主軸にするか（P2の課金検証で決定）。
2. **対象年齢と法務**: 未成年利用を許すか。許す場合、UGC・課金・LLM出力の各規制対応が必要。
3. **IPコラボの余地**: キャラクター性が強いプロダクトのため、既存IPとのコラボ（公式ペルソナ）は強力な獲得手段になり得る。権利設計を早期に検討。
4. **国際化**: UIとペルソナテンプレートの多言語化タイミング。LLM自体は多言語対応のため障壁は低い。
5. **エージェントの自律活動**（スケジュール実行・エージェント同士の社会）はP3の目玉候補だが、コストと安全性の検討が別途必要。
